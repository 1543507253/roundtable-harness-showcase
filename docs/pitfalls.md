# 踩坑记录 · 12 条静默失效

> 来源：开发过程中登在 `docs/DEV-LOG.md` 的 42 条问题台账，这里挑出 12 条。
> 挑的标准只有一个：**当时完全不知道原因，最后靠证据定位的**。笔误、装错包、改个拼写这类不收录。
> 每条按同一个结构写：现象 → 怀疑 → 验证手段 → 结论。结论之后才是修法。

---

## 一、写了代码 ≠ 代码在跑（4 条）

这类坑的共同点是：**没有任何报错**。功能没生效，日志不响，界面不提示，一切看起来正常。

### 1. prompt 注入段早就在，但从来没执行过

- **现象**：共识注入段在 `buildPrompt` 里写得清清楚楚，但跑起来的 prompt 里找不到这段。
- **怀疑**：字符串拼接写错？条件判断永远为 false？
- **验证**：不猜，直接在 `buildPrompt` 入口打印入参——ctx 参数是 `undefined`。
- **结论**：`buildPrompt` 消费端有代码，但三处 `runDebate` 调用**全都没传这个参数**。生产端没接线，消费端写得再对也没用。
- **修法**：把参数组装收成一个 `buildPromptCtx(name)`，三处调用点按各自语境接线（MCP/HTTP 走 `.then` 链，会议异步走 `await`）。
- **教训**：新增任何"注入"，两端都要查——**消费端有没有用，生产端有没有喂**。只查一端，必然漏。

### 2. 单测命中，端到端 0 命中——最后是编码问题，不是逻辑问题

- **现象**：检索注入跑完，`exp_log` 恒为 0 条。单测 `queryExperience` 手动调能命中 2 条。
- **怀疑**：检索代码没执行？还是执行了但没命中？
- **验证**：加临时 `[DBG-EXP]` 日志重启，输出 `topic.len=44 snap=2 hits=0`——**执行了，但 0 命中**。
- **继续怀疑**：既然是 0 命中，问题在输入。把 topic 打出来，是一串乱码。
- **定位**：Windows 下用 curl 发中文，服务端收到的是 GBK 字节，检索自然匹配不上。换 Python `ensure_ascii=False` 发 UTF-8 请求，`hits=1` 且成功落盘。
- **再往回看**：命中了，但 REST 端点里压根没接检索——只加在了 MCP 工具入口。
- **教训**：一次排查，两个证据互相印证。**同一逻辑存在多个入口时，验证必须覆盖实际被调用的那个入口**；怀疑代码之前先打印输入，别直接改代码赌。

### 3. 主判官每轮都在发言，数据里 0 条

- **现象**：日志明确打印 `[debate] moderator round N`，但前端"主持发言"计数一直是 0。
- **怀疑**：主判官的结果被丢弃？还是写库时被过滤？
- **验证**：查落库条目——存在，但 `moderator` 标记为空。
- **结论**：`onMessage` 里有个字段白名单，没有 `moderator` / `phase` 两个字段。引擎产出的标记在透传层被**静默剥掉**，条目变普通发言。
- **修法**：两处 `onMessage` 都补透传。
- **教训**：**字段白名单是静默失效的高发区**。加字段必须同步检查所有透传层，写漏不会报错，只会数据缺一块。

### 4. 后端改了不生效——旧进程还占着端口

- **现象**：改完代码重启，行为跟没改一样。日志里有一句"端口已被本服务占用，复用现有后端"。
- **怀疑**：文件没保存？构建没生效？
- **验证**：查端口占用方的 PID 和启动时间——是几小时前的旧进程。
- **结论**：`taskkill` 那一步没杀成功。管道式 `Stop-Process` 对这类进程无效，旧进程继续占着 3721，新进程干脆静默复用旧后端。
- **修法**：先按命令行匹配收 PID，再 `Stop-Process -Id` 定点杀，杀完核对 `/health` 的启动时间。
- **反坑**：按命令行模糊匹配时**不能匹配过于宽泛的串**，否则会把当前正在执行的 shell 一起杀掉（实测会发生）。

## 二、数据静默消失（3 条）

不报错，不提示，重启之后数据就少了一块。

### 5. 改了 JSON 文件，重启后测试数据没了

- **现象**：为了造测试数据，直接改 `data/*.json`，服务跑一轮后改动消失。
- **结论**：服务在内存里持有全量数据，下一次落盘会用内存覆盖文件。**运行中改文件 = 白改**。
- **正确姿势**：停服务 → 改文件 → 启服务 → 验证。

### 6. 并发写同一个 JSON，进程被杀

- **现象**：辩论中途服务突然退出，没有异常栈。
- **结论**：两个异步写同时落同一个文件，写坏了。fire-and-forget 的 async write 更是定时炸弹。
- **修法**：原子写（临时文件 + rename）+ 串行化写入队列。

### 7. `Object.keys(x).length || x.length` 把字段整个吞掉

- **现象**：某个字段明明赋了空对象，序列化后整个 key 消失。
- **结论**：`x = {}` 时，`Object.keys(x).length` 得 0，`||` 走到右边 `x.length` 得 `undefined`，`JSON.stringify` 就把 undefined 字段直接丢掉。
- **修法**：`Array.isArray(x) ? x.length : Object.keys(x || {}).length`，不要用一个 `||` 兼容两种类型。

## 三、判据写宽了，误判比漏判更贵（2 条）

### 8. 收敛检测：把"引用别人的反对"算成自己反对

- **现象**：收敛卡里出现大量分歧，人工核对发现那些人其实都同意。
- **结论**：反对词表用了宽词——只要句子里出现"反对""站不住"就算反对，于是"他说的那点站不住，但我同意主体方案"被判成反对。
- **修法**：换成**严格第一人称词表**（我不同意 / 我反对 / 我质疑 / 我保留），并要求词前有第一人称。实测 4 条误报降到 0。
- **教训**：判据宁窄勿宽。**漏判会让人再问一轮，误判会直接把结论改错**。

### 9. 谈判型发言（接受 A、拒绝 B）一刀切后全员判 0

- **现象**：一整轮都很正常，收敛值却是 0。
- **结论**：规则写成"出现拒绝词 → 该席计 0"。但谈判型发言本来就是"接受一部分、拒绝一部分"，一刀切等于全员弃权。
- **修法**：按"接受=1 / 部分接受=0.5 / 拒绝=0"加权取均值，不归零。
- **教训**：多席位的量化判据，**先想清楚"部分成立"该怎么计分**，否则二值化会把真实分歧和真实共识一起抹平。

### 10. 议题被 AI 顺手改了（这条是用户当场发现的）

- **现象**：用户输入一长段议题，系统给出来的议题变成了摘要，还被截到 110 字。
- **结论**：代码里 `topic = summary || value`，AI 提炼的摘要顶替了原话。
- **修法**：`topic` 永远等于用户原话，一字不改；AI 提炼只允许当标题显示。
- **教训**：**用户的原话是不可变输入**。任何"顺手优化"都是在替用户改题，评审对象错了，后面全错。

## 四、前端与工具链（2 条）

### 11. 折叠功能写了但永远不触发

- **现象**：超过 220 字的消息本该折成 3 行，实际全部展开。实测 `clientHeight === scrollHeight`，说明根本没裁。
- **结论**：折叠标记挂在元素自身（`class="msg-body msg-fold"`），但 CSS 写的是后代选择器 `.msg-fold .msg-body`——永远匹配不到自己。
- **修法**：改复合选择器 `.msg-body.msg-fold`。
- **教训**：class 挂在同一个元素上时，**后代选择器必然失效，而且不报错**。

### 12. 中文经 curl 发出去变乱码

- **现象**：Postman 测没问题，脚本测命中率恒 0。
- **结论**：Windows 下 curl 默认不走 UTF-8，中文到服务端已成 GBK 字节。
- **修法**：API 验证一律用 Python `urllib` + `ensure_ascii=False`；写完文件必须过一遍编码检查。
- **延伸**：用 Python 重写 JS 文件时，`"\n"` 会被写成真实换行，把 JS 字符串写坏——改完必须 `node --check`。

## 这 12 条背后的同一件事

没有一个坑是"想错了"，全部是**"以为它在跑，其实没跑"**。所以这个项目的排查流程被固化成一条纪律：

1. 疑似 bug 先**加日志证实它有没有执行**，不证实不改代码；
2. 同逻辑多入口，验证必须**覆盖真实入口**；
3. 改完必须有**可断言的证据**（状态断言的接口调用、日志、`node --check`），不看界面"感觉对了"；
4. 修完登记台账，写"发现过程"而不是结论——因为过两周只记得结论，会再踩一次。
