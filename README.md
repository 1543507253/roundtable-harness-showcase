# Roundtable Agent Harness · 多智能体协作运行时

> 多个模型按角色分工、按 9 步流程推进，靠规则化判据把讨论收敛成一份结论，全程可审计。
> 一次项目评审，从「开几天会」压缩成「几分钟出一页能签字的决策卡」。

**在线看：[1543507253.github.io/roundtable-showcase](https://1543507253.github.io/roundtable-showcase/)**
**本地看：[`index.html`](index.html)**（单文件，无外链，直接浏览器打开即可）

---

## 它到底解决什么问题

市面上的多智能体产品，绝大多数在优化「讨论的质量」：让对话更聪明、更全面、更多点子。
但真实的评审现场，缺的从来不是点子——是**一句能签字的话**，和**签字之前的证据**。

所以这个项目的设计目标反过来：**不追求讨论的丰富度，追求结论的可签性**。

具体表现为三个约束：

1. **每个数字必须能追到来源**，追不到就标「待查证」，不允许拿宏观数据做微观归因；
2. **结论要过代码级判据**，不是模型自己说「我觉得可以」；
3. **验收角色独立于讨论过程**，只看交付物，只判通过或不通过。

---

## 三个"只有代码能答"的问题

这是这个项目真正的差异化，也是面试中最值得展开的部分：

**① 证据边界是靠 prompt 约束，还是靠代码？**
三层：prompt 只定规矩（第一层），`auditHardGates()` 与 `checkCardArithmetic()` 把规矩变成可执行的判定（第二层），独立验收角色不看过程只看产物（第三层）。模型说了不算，正则和算式说了算。

**② 反驳机制是预设话术，还是真的会反驳？**
实测中，角色槽位会**反驳议题本身**。例如把「做不做」与「唯一优先」捆成二选一的题，被当场拒绝：

> 部分接受，但我要先反驳议题本身：把「做不做」和「唯一优先」捆成一个二选一，讨论就被拖到预算、开关、排他纪律上，没人回答最该先答的一句——过去哪一次演示事故，是因为版本链没有分级 state 丢的？

这不是 prompt 里写好的模板句。同一套准则在别的会话里跑，没有出现这句话；它也出现在准则的「翻车记录」里——某次组建把游戏创意审成了十年期技术立项，被记下来当反面案例。**机制是长出来的，不是预设的。**

**③ 多智能体是真接入，还是循环调 API？**
33 个 MCP 工具、SSE 与 Streamable HTTP 双传输。外部 agent 用 `join_context` 自述身份 → `list_pending_turns` 取待发言 → `claim_turn` 认领，可以作为独立角色槽位参与同一场协作。四个编码 agent（Hermes / opencode / WorkBuddy / CodeBuddy）曾同时接入同一套上下文，共享同一份会话与同一套准则。

**收录**：演示页、架构说明、真实讨论摘录、12 条踩坑记录、关键设计的骨架级代码摘录。

**不含**：协作内核实现、33 个 MCP 工具的代码、前端看板、智能组建准则全文、行业基准库、任何真实评审数据。

完整实现是私有仓库。需要代码走读的，可以在面试中申请只读权限。

这个选择不是藏私，而是这个项目最值钱的部分不是「代码量」，而是**判据怎么定**——收敛阈值为什么是 0.6、连续 2 轮为什么能防误判、反对词表为什么要限定第一人称、组建准则为什么要先审题三步。这些在 [`docs/architecture.md`](docs/architecture.md) 和 [`docs/pitfalls.md`](docs/pitfalls.md) 里讲的是**结论和推理**，不是配方。

## 诚实边界

1. 不训练、不微调，智能全部来自自备 API key；
2. 单机单进程，适合一个团队评审，不是全公司 SaaS；
3. 审计是应用级留痕，不是法律级存证；
4. **不做自动检索、也没有 RAG**：没有切块、没有向量库、没有召回率——证据靠半自动注入 + source_url / published_at / retrieved_at 三字段强制校验；
5. 没有用户级鉴权，会话之间靠独立上下文隔离；
6. 外部 agent 入席接口已通，但 136 个角色槽位仍以本机 HTTP 为主，外部 agent 真实入席只到联调级验证；
7. 已知缺陷：决策卡的「核心假设」段曾出现带假来源的数字；验收角色自算过一次错（说回收期 4.5 年，实为 5.1 年）；收敛判据偏松。都在修。
